ADR-001　系统主体：监管方

项内容
状态已采纳（甲方确认）
背景参考平台含「执法检查」「整改通知单」，区域为四川省/成都市，判断为监管方视角。
决策以监管方为主租户，运维单位与企业作为入驻租户；一套系统、多租户隔离、按角色出四套工作台。
后果
  • 权限模型必须是「功能权限 × 数据权限」，运维单位只能看自己承接的站房，企业只能看本企业。
  • 考核、排名、督办、执法检查是一等公民，不是附加功能。
  • 平台侧要能配置"谁给谁做运维"（站房—运维单位—合同绑定），换运维单位要留历史。
  • 数据上报口径必须能对上级平台解释，否则监管方第一个质疑。
被否方案纯运维公司内部系统（SaaS 单租户）：无法承载执法与考核，且与参考平台形态不符。

ADR-002　数据源：双模适配，先直连后对接

项内容
状态已采纳（甲方确认：直连数采仪）
背景数据可能有三种来源：① 现场数采仪直接上报我方平台；② 从国发/省平台取数；③ 甲方已有平台转发。三者的能力边界差别极大。
决策采用 DirectProvider：数采仪 TCP 直连。报文经 Netty 接入、SM4 解密、按 MN 归属站房后落库；原始报文、双维度标记、工作参数、反控全部可用。上级平台对接（UpstreamProvider）本期不做，仅保留接口形状。
 
IngestProvider（接口）
├─ DirectProvider      现场机 TCP / HTTP 直连（本期实现）
│    · 能拿到：原始报文、双维度标记、工作参数、日志、反控
└─ UpstreamProvider    对接国发/省平台（预留）
     · 通常只能拿到：分钟/小时数据 + 部分标记；原始报文与反控大概率没有
能力自建直连对接上级平台影响的模块
分钟级原始报文有通常没有原始数据页、报文审计、CRC 统计
双维度数据标记有部分有附录 G 有效性判定、标记 ⇄ 工单核验
工作参数 / 变更有多半没有参数监控、参数变更告警
设备 SN / 密钥状态有看平台开放程度联网监测、SN 一致性校验
远程反控（校时/读参）有基本没有远程反控模块
时效性实时（秒级）取决于上级平台同步周期（常为小时级）报警延迟、P1 触达 60 秒指标
这条必须写进合同

如果最终走"对接上级平台"，P1 报警 60 秒触达、原始报文追溯、远程反控这三条验收指标都不成立。要么甲方接受降级指标，要么现场改造把数采仪指向我方平台。现在不定，验收时一定吵。

落地做法

  • 配置项 INGEST_MODE=direct | upstream，启动时决定装配哪个 Provider（当前骨架已按此设计，TcpServer 在非 direct 模式自动跳过）。
  • 业务层只依赖「标准化事件」，不依赖报文格式；换数据源不改报警、报表、工单。
  • 两种模式并存时（部分点位直连、部分对接），按站房维度路由，而不是全局开关。

ADR-003　微信生态：已认证 + 公网部署

项内容
状态已采纳：公众号「海兰天澄」，主体 成都海兰天澄科技股份有限公司（四川成都，已认证）
决策以「海兰天澄」认证服务号为公众号通道（具备模板消息/订阅通知能力），小程序作为查看与作业入口；两者都不承担"必达"责任。系统部署在公网，数据层可下沉内网。
后果
  • 公网暴露接入端口（20000）与 Web，必须做：WAF/防火墙白名单、接入令牌、TLS、限流、防重放；等保二级。
  • 小程序需要已备案域名 + HTTPS + 服务器域名白名单，提前 2~3 周准备。
  • 订阅消息仍需用户逐次授权，产品上要设计"用一次攒一条"的授权引导。
  • 公众号若为订阅号则无模板消息能力，必须确认是认证服务号。
