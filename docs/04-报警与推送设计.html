01 设计原则与分级

1.1 四条原则

原则说明
宁可少报，不可乱报每条报警都必须"可处置"。报了没人能处理的，不进报警，进报表。
分级即路由级别不是标签，直接决定发给谁、多久发、要不要打电话。
证据随报警走报警消息里必须带：哪个站房、哪个因子、什么时候、现在值、限值、曲线截图入口。
状态单向可追OPEN → ACK → PROCESSING → CLOSED，每次流转留痕，不允许多端各改各的。

1.2 分级定义

级别定义触达要求典型场景
P1可能构成违法或导致数据中断60 秒内触达；未认领 15 分钟升级；夜间电话兜底超标、离线超 2h、密钥过期、SN 不一致、参数被改、虚假标记
P2影响数据质量或运维履约5 分钟内触达；未处理 4 小时升级有效数据率不达标、校准超期、恒值、标样核查不合格、工单超时
P3提示类，可批量处理日报/汇总推送合同到期、证书临期、物资临期、视频离线

02 规则模型

规则采用「对象 + 条件表达式 + 持续时长 + 抑制窗口 + 通知策略」五元组，全部界面可配，新增规则不改代码。

{
  "rule_code": "DATA_OVER_LIMIT",
  "name": "污染物超标",
  "category": "DATA",
  "level": "P1",
  "target": { "station_type": ["WASTE_WATER","WASTE_GAS"], "factors": ["*"] },
  "expression": "value > limit && dev_flag == 'N' && prod_flag in ['N']",
  "duration_sec": 180,
  "suppress_sec": 3600,
  "window": { "time": "00:00-23:59", "days": "1-7" },
  "channels": ["FEISHU", "WXA"],
  "escalate": { "900": "MGR", "1800": "ORG", "2700": "PHONE" },
  "enabled": true
}

2.1 表达式可用变量

变量含义示例
value当前值（折算/实测按规则声明）—
limit该因子执行限值—
dev_flag设备标记N/D/C/M/T/Td
prod_flag工况标记N/St/Sd/B/F
duration条件持续秒数180
valid_rate时段有效率0.86
gap_min连续缺失分钟数120
variance窗口内方差（恒值判定）0
last_cal_days距上次校准天数35

03 内置规则清单

3.1 数据类（DATA）

规则判定级别抑制说明
DATA_OVER_LIMIT折算值 > 限值，持续 ≥3 分钟P1同站同因子 1h排除 D/C/M/T 标记与停运时段
DATA_DEAD_VALUE连续 10 条数值完全相等（方差=0）P24h对应"数据保持"，2025 明令禁止
DATA_NEGATIVE浓度 < 0 且未修约P24h零点漂移，需校准
DATA_ZERO非停运时段浓度恒为 0 且流量 > 0P24h疑似未采样/稀释
DATA_OVER_RANGE值 ≥ 量程上限P22h需核查量程设置
DATA_JUMP相邻分钟变化率 > 300%P32h仪表异常/信号干扰
DATA_MISSING连续缺失 > 30 分钟P11h区分停电/断网/停机
DATA_OFFLINE数采仪离线 > 30 分钟P11h按 MN 维度

3.2 有效性类（VALIDITY）

规则判定级别抑制说明
VAL_RATE_LOW当日有效率 < 90%P2日次日 01:00 计算
VAL_RATE_CRITICAL当日有效率 < 60%P1日触发考核扣分
VAL_LONG_MAINT连续 M 标记 > 24 小时P112h疑似以维护逃避监管
VAL_LONG_FAULT连续 D 标记 > 24 小时P112h故障长期不修
VAL_FAKE_MARK标记 C/M/D 但无对应运维记录P16h核心差异化能力
VAL_MISS_MARK有校准记录但时段标记为 NP26h漏标，影响有效率
VAL_UNCONFIRMED联网未确认即上报数据P1日确认前数据无效

3.3 设备类（DEVICE）

规则判定级别抑制说明
DEV_KEY_EXPIRING密钥 ≤7 天到期P23d提前介入，避免断数
DEV_KEY_FAIL密钥更新失败 ≥2 次P16h派人现场处理
DEV_KEY_EXPIRED密钥已过期P12h解密失败，整站中断
DEV_SN_MISMATCH上报 SN ≠ 台账 SNP1日疑似翻新机/私自换机
DEV_SN_MISSING当日 0:05 未上报 SNP2日—
DEV_PARAM_CHANGE量程/斜率/截距发生变化P11h每次都要通知，不抑制过久
DEV_PARAM_FREQ7 天内参数变更 > 3 次P17d频繁调参属高危行为
DEV_PARAM_MISMATCH运行参数与备案参数不一致P27d—
DEV_CLOCK_DRIFT现场机时间偏差 > 60 秒P2日可一键校时
DEV_QC_FAIL标液核查不合格P1—该时段数据回溯判无效
DEV_CAL_OVERDUE距上次校准 > 规定周期P27d周期按因子类型配置
DEV_CERT_EXPIRECCEP/检定证书 ≤30 天到期P37d—

3.4 运维类（OPS）

规则判定级别抑制说明
OPS_PLAN_MISSING本月应运维站房未排期P27d计划覆盖率缺口
OPS_TASK_OVERDUE任务超过 deadline 未完成P21d—
OPS_RESP_SLOW下发后 30 分钟未接单P26hSLA 响应项
OPS_ARRIVE_SLOW接单后 2 小时未到场P26h—
OPS_FIX_SLOW到场后 24 小时未修复P112h故障类任务
OPS_REMOTE_CHECKIN打卡距离 > 300 mP1—异地打卡，记录不可用
OPS_NO_RECORD任务完成但无运维记录P2——流程断点

规则判定级别抑制说明

04 降噪

没有降噪设计的报警系统，一周之内就会被用户关掉。以下五层必须全部实现：

机制做法示例
防抖（持续时长）条件需连续满足 N 秒/条才产生事件超标持续 3 分钟才报
抑制窗口同对象同规则 N 秒内只产生一条1 小时内同一因子不重复报
聚合同站房多因子同时异常合并为一条"站房异常"一次推 1 条而非 8 条
依赖抑制父对象故障时抑制子对象报警数采仪离线时不再报"数据缺失"
维护期静默已排期维护/校准时段自动静默校准 30 分钟内不报数据异常
一个容易踩的坑

"维护期静默"必须以已审核通过的运维记录为依据，不能用"计划"静默——否则只要排个计划就能屏蔽一切报警，反而成了造假工具。

5.2 自动恢复

数据类报警（超标、缺失、离线）支持自动恢复：条件不再满足持续 N 分钟后自动置 CLOSED 并推送"已恢复"消息。运维类、监管类报警必须人工关闭，防止"自动消失"。

07 四渠道能力与真实限制

这一节请在需求评审时明确告知甲方

微信生态的触达能力有硬约束，不是"接了就能保证收到"。公众号模板消息早已改为订阅通知，小程序长期订阅仅限特定类目。把不可靠的渠道写成"主通道"，验收时一定会扯皮。

渠道能做什么硬限制 / 前提建议定位
飞书应用消息、交互卡片（按钮回调）、@人、群机器人、加急需企业自建应用 + 权限审批 + 公网可访问的回调地址；外部用户（企业、监管）通常不在同一组织，需通过群机器人或外部群主通道 运维团队内部
微信公众号模板消息 / 订阅通知（服务号）必须认证服务号；用户须关注并绑定 openid；订阅通知为"一次授权一次推送"，触达率不可控辅助 面向企业与监管的日报/通知
微信小程序订阅消息（一次性）、小程序内报警列表长期订阅仅限特定类目（环保类大概率不获批）；一次性订阅需用户每次点击授权主入口 列表比消息可靠
短信纯文本，必达性最好按条计费；模板需报备；营销类时段限制兜底 夜间 P1

7.1 渠道决策矩阵

级别时段渠道组合

P120:00–08:00飞书卡片 + 短信立即发（夜间只看短信）
P2全天飞书卡片 + 小程序订阅消息

08 飞书实现方案

8.1 两条路径

方式优点限制适用
群自定义机器人 Webhook5 分钟接入，无需审批只能发消息，不能收回调；无法 @ 指定人（只能 @all 或 @手机号）快速验证、P3 汇总
企业自建应用 + 交互卡片可发卡片、可带按钮回调、可 @人、可发单聊、可加急需管理员创建应用、申请权限、配置事件订阅地址（公网 HTTPS）正式方案

8.3 回调处理

回调动作服务端处理返回
ack 认领校验操作人权限 → 写 alm_action → 更新 event.status=ACK → 通知其他端刷新toast「已认领」
close 关闭要求填写处置说明（弹表单）→ 写 action → CLOSED更新卡片为灰色
重复点击幂等判断（已 ACK 则忽略）toast「已被 XXX 认领」

回调地址须在 3 秒内响应，业务处理走异步，避免飞书重试导致重复。

09 微信公众号实现方案

9.1 前提条件（逐条确认，缺一不可）

  • 主体为已认证的服务号（订阅号无模板消息能力）。
  • 已配置服务器地址（公网 HTTPS）、Token、EncodingAESKey。
  • 用户已关注公众号，且系统通过网页授权拿到 openid 完成绑定。
  • 消息模板已在后台申请通过（环保告警类模板需要合理措辞，避免被判营销）。

9.2 绑定流程

用户在小程序/Web 登录 → 点击"绑定微信通知"
  → 跳转公众号网页授权（snsapi_base 静默 / snsapi_userinfo）
  → 回调带回 code → 换取 openid/unionid
  → 写入 msg_subscribe（user_id ↔ openid）
  → 页面提示"已开启，未关注请先关注"

9.3 降级方案

若甲方没有认证服务号，公众号推送直接不成立。替代方案按优先级：

① 小程序订阅消息（推荐）；② 服务号内嵌 H5 + 站内消息（用户主动查看）；③ 短信兜底；④ 若甲方是企业微信用户，改走企业微信应用消息（能力接近飞书）。

10 小程序订阅消息方案

项说明
模板类型优先申请"设备故障提醒""报警通知"类模板；长期订阅需类目支持，环保类通常只能一次性订阅
授权策略用户进入小程序首页时批量请求授权（一次最多 3 条）；每次处理报警时再补一次授权，形成"用一次攒一条"的循环
参数thing1 站房名 / phrase2 报警类型 / time3 时间 / thing4 处置提示
失败处理43101（用户拒收）→ 标记该用户不可用，转飞书/短信
可靠性不承诺必达；所有报警在小程序"报警列表"中永久可查，消息只是提醒

11 值班表与免打扰

机制规则
值班表按组织 + 日期 + 班次（白/夜）配置，支持导入；当天值班人优先接收 P1
免打扰P2/P3 在 22:00–08:00 不推送，合并到次日 08:30 汇总；P1 不受免打扰限制
休假代理人员请假时可指定代理人，代理期内接收全部消息
渠道偏好用户可自选"仅飞书"或"飞书+短信"，但 P1 的短信由系统强制，不可关闭

12 可靠性设计与验收

12.1 发送可靠性

环节策略
异步解耦报警产生后只写库 + 投递 MQ，推送由独立消费者处理，推送失败不影响报警本身
重试指数退避 3 次（5s / 30s / 120s），仍失败则降级到下一渠道
限流单用户 1 分钟 ≤ 5 条，超出合并为摘要，防轰炸
去重event_id + channel + receiver 唯一约束
可观测发送成功率、平均耗时、失败 Top 错误码按小时统计
补偿每日 02:00 扫描"未成功送达的 P1"，重新推送并生成待办

12.2 验收口径

  • P1 报警从产生到飞书可见：P95 ≤ 60 秒。
  • 推送失败可查：每条报警可看到"发了哪些渠道、成功几个、失败原因"。
  • 端到端一致：飞书认领后，Web 与小程序在 5 秒内同步状态。
  • 压测：1 分钟内产生 200 条报警，无消息丢失、无重复推送。
